# Admin order deletion policy

The admin API requires a signed, named admin session and approved browser origin. The user presses **Delete Order**, then **Yes, delete permanently** once. The client sends the exact order ID and protected `DELETE ORDER` server-side confirmation; the database RPC is restricted to `service_role`, so server-side guards remain in force.

| Order state | Result |
| --- | --- |
| Practice or ordinary `new`/`processing`, including archived | Eligible when payment is COD, no active courier booking remains, and Meta Purchase delivery is complete or absent. An unfulfilled outstanding stock reservation is restored once. |
| Cancelled, including archived | Eligible when the courier was never booked or its cancellation is confirmed. Stock is restored only if the reservation flag is still set and no shipped or delivered history exists. |
| Shipped or courier booking/cancellation in progress or uncertain | Blocked until delivery or confirmed courier cancellation and reconciliation. |
| Delivered COD | Eligible with additional confirmation. The operational row is removed; stock is never restored. Restricted order, item, status, courier, and financial evidence remains. |
| Non-COD payment, unfinished Meta Purchase reporting, conflicting delivered courier evidence, unknown status, or missing itemized/stock data | Blocked pending reconciliation. |

Deletion does not contact PostEx, issue refunds, change settlements, or modify external order sheets. Delivered Meta outbox rows remain attached to the public order ID; unfinished outbox rows block deletion. Sent email event metadata is retained; unsent order emails are removed. The deletion audit records the public order ID, named actor, time, and outcome without customer PII. A restricted evidence table keeps the order snapshot and dependent records, and a tombstone prevents reuse of public order IDs, internal IDs, and checkout idempotency keys.

The evidence tables have RLS enabled, are accessible only to the server service role, and reject updates or deletes. **Approved retention approach:** The operational order disappears from the admin lists immediately after a successful database transaction. Practice-order evidence and successful deletion audits are retained for 30 days. For real orders, restricted evidence and the corresponding successful audit are retained until the later of seven years after order creation and one year after deletion. This is a conservative operational window reflecting Pakistan FBR's six-year recordkeeping guidance; confirm applicability with the business's tax adviser. Rejected deletion audits are held for one year. Tombstones storing only order/internal IDs and checkout idempotency keys remain indefinitely solely to prevent identity reuse. Existing historical sent-email and Meta reporting records are not automatically purged by this workflow; review their independent retention obligations. Marketing attribution tokens are excluded from new evidence snapshots. Disposal is a controlled DBA action, not automatic: after confirming no open tax, courier or legal proceeding, a DBA may invoke `public.purge_expired_order_deletion_records` in bounded batches. Any order under legal hold is excluded. This procedure is not executable by the storefront/admin service role. The application has no separate payment or settlement ledger; COD fulfillment evidence is preserved here, but any external courier or accounting records remain external and must be reconciled before an administrator uses deletion.

Apply both `20261113000000_safe_all_order_deletion.sql` and `20261113000001_deletion_dashboard_metrics.sql` before deploying the admin app. The second migration keeps historical dashboard totals while operational queues use live orders. The old two-argument RPC remains during rollout but cannot delete ordinary orders because it lacks the extra confirmation. Neither migration is applied to production by this PR.

### Release and recovery runbook

1. Confirm the target is VoltGear Supabase project `zeuhfqevqjkbzwdaxjuv`, review the live migration ledger, and confirm the last baseline includes `20261112062924_audited_admin_order_deletion` and `20261112062940_meta_purchase_matching_fields`. Confirm the retention schedule above is appropriate for the business, verify no active legal holds and verify a recent restorable database snapshot. Stop if any prerequisite differs.
2. In a disposable local Supabase project with distinct project ID and ports, apply the full migration chain. Run `supabase/tests/safe_all_order_deletion.sql` with `psql -v ON_ERROR_STOP=1` against that project's database; all fixtures and assertions are inside `BEGIN`/`ROLLBACK`. Run `VOLTGEAR_QA_DB_CONTAINER=<local QA container> node supabase/tests/concurrent_order_deletion.mjs`; this commits synthetic fixtures only in the disposable database. Confirm one deletion, one audited rejection, one tombstone and one stock restoration. Dispose of the QA project afterward.
3. With separate explicit production authorization, apply `20261113000000_safe_all_order_deletion.sql` and then `20261113000001_deletion_dashboard_metrics.sql` to the confirmed VoltGear project. Verify both versions, RPC privileges, the dashboard function and a read-only sample before deploying the admin code. Never deploy the new admin before both migrations succeed.
4. If either migration fails, stop before admin deployment and preserve database logs and snapshot. Do not rerun blindly or mark the migration applied manually. Reconcile partial DDL and migration ledger in a reviewed transaction or restore the snapshot under DBA supervision.
5. If the admin release fails after schema deployment, redeploy the prior admin build and leave the additive evidence/tombstone schema intact. If deletion must be frozen immediately, an authorized DBA can revoke `EXECUTE` on both `public.admin_delete_order(text,uuid,text)` and `public.admin_delete_order(text,uuid)` from `service_role`, then verify calls fail. Regrant only after a reviewed fix. Do not drop immutable evidence or tombstones as an automatic rollback; reconcile any already deleted order from restricted evidence and external courier/accounting systems under a separate recovery plan.

### Evidence policy references

- FBR official income tax return guidance: https://fbr.gov.pk/categ/file-income-tax-return/51147/80860/71163 (six years of income tax records, where applicable).
